# Agent Instructions

This repository is a knowledge artifact about the **authoring vocabulary of point-and-click
adventure games**, maintained alongside the development of an engine for them in Rust. Its
central question is: what is the smallest set of authoring primitives that can express a
classic point-and-click adventure without escaping to a general-purpose scripting language?

Read that as a constraint on your work, not just as context. A node earns its place by
being something the existing vocabulary cannot say. Before adding a class or a primitive,
the first move is to try to express the thing with what is already here and record what
failed — a negative result about expressiveness is the most valuable kind of node this
corpus holds.

Then read what you wrote. **If expressing it meant writing the same thing more than once,
ask the question again about the copy.** The vocabulary could say each instance and could
not say what they have in common, which is the same negative result one level up. A copy is
the residue a question asked at the wrong level leaves behind, and this rule missed the
pressure five times before that was noticed — once in this repository's own test suite. See
`.yidam/decisions/duplication.yml`.

This repository is a living knowledge artifact. Its git history is the knowledge graph:
files are nodes, commits are knowledge events, links are edges.

This repository adopted **no kuten** at genesis. The one profile the template ships,
`inquiry`, was stated and declined: no profile there was recognized as describing what this
corpus is for. That is a supported state — `yidam kuten check` reports it as one and exits
zero — and it is deliberately not a placeholder. A declaration diverged from on the first
commit defeats the layer's only purpose. Adopt one later by a `decide:` commit carrying the
record; do not edit the vendored profile, which is discarded on the next re-vendor.

The declaration narrows the loop and may not widen the model, and **it binds nobody**:
divergence from it is a question for a person, not a defect. `yidam kuten check` reports
where this repository's history and its declaration disagree, writes nothing, and exits zero.

## Conduct norms

**Commit deliberately.** Every commit is a permanent knowledge event. The message should read
as a legible description of what changed and why — not a diff summary. Keep epistemic commits
(understanding added or revised) distinct from operational commits (extraction, refresh,
regeneration) — and the distinction is carried by the **closed verb vocabulary** in
[GRAPH.md](.yidam/.vendor/prelude/GRAPH.md), not by style alone. Every subject begins
`<verb>: `, the verb stands alone with no `(scope)` suffix, and `yidam lint --commits`
reports anything outside the list. A merge deserves a written subject too; git's default
names the ref and not what joining it meant.

**Link generously.** New nodes must connect to existing ones. Orphan files weaken the graph.

**Stay within scope.** Do not add nodes speculatively. Add a node when an edge needs a target
that does not yet exist.

**Make synthesis explicit.** Adding edges between existing nodes is a first-class
contribution, not housekeeping.

**Preserve provenance.** Do not delete or rewrite committed nodes without a record of why.

**Tag your claims.** Non-obvious claims carry `[verified]`, `[inference]`, or `[open]`.
Untagged inference is the problem the tags exist to prevent.

**Do not confuse the corpus with the engine.** This domain has a hazard most do not: the
subject of study is a Rust program, and `crates/` also holds Rust. They are different things.
`crates/` is the instrument that makes the corpus queryable — a coverage calculator, an index.
The engine under study is described by `subsystem` and `data-format` nodes, and its code, when
it exists, is not the corpus's to hold. A renderer does not belong in `crates/`.

**A claim about prior art needs a source.** `[verified]` says a committed source supports the
claim, not that you are confident. Engine documentation and source releases are reachable and
citable; recollection of how SCUMM behaved is `[inference]` at best, however strong. This is
the failure mode most likely to enter this particular corpus, because these engines are widely
described secondhand and the secondhand accounts disagree.

**Re-read the source at the point of inference, not at the point of retrieval.** Three
conclusions here have been overturned by pages this corpus already held: the AGS pick-up mode,
which conversation shape is the base case, and what AGS's dialog sub-language demonstrates about
bounded languages. None of the three was careless retrieval. In every case the material was
fetched and recorded accurately, and then reasoned about from memory of the conclusion rather
than from the record — and in the first, the catalog ledger had already written down the exact
gap the claim asserted past.

The third was caught before it reached anything rather than after. The whole argument turned on
one property of one page, so the page was fetched again to check that property specifically, and
it carried a second escape-hatch quote the first reading had never recorded. **A ledger only pays
if it is re-read at the point of inference.** When a conclusion is about to rest on a source,
open the source; a re-fetch costs a minute and two phases here have been spent not doing it.

**The ontology is a record too, and so is the list of open questions.** The same failure arrived
a fourth time from a different direction: a worked specimen marked four things the vocabulary
could not express, and three of them were already expressible by relationships declared since
genesis. Before adding a class, a relationship or a property, run `yidam open-questions` and read
the `.ont.yml` of every class involved. One of the properties added that way had been requested
by name, in prose, in a corpus node, two phases earlier — and was arrived at from the opposite
end without anyone noticing.

A worked example is an excellent detector of trouble and a poor diagnostician of it. Treat every
site it flags as worth checking and none of them as diagnosed.

## `design/` — where this repository proposes rather than records

The corpus is documentary. Every node says what some engine did, what some source states, or
what follows from those, and the three claim tags are the whole vocabulary available — none of
them permits asserting intent. That is the discipline the corpus is worth.

The central question outgrows it. Comparing what other engines chose works for exactly as long
as somebody else has built the thing being compared, and
[`data-format/interaction-table.yml`](.yidam/corpus/data-format/interaction-table.yml) reached
the end of that: AGS built a bounded dialog sub-language and documented that it was not enough,
SCUMM had no declarative layer to escape from, and nobody built the middle. Recording that
nobody did is a corpus claim. Saying what the middle should be is a proposal, and proposals go
in [`design/`](design/).

**The one rule it relaxes: a document there may assert intent.**

**What it does not get to relax:**

- **Provenance.** A claim about an existing system carries the same tag it would carry in the
  corpus and cites the same catalog entry by link. `[verified]` still means a committed source
  supports it, and an aggregator still cannot carry one. A design is free to propose; it is not
  free to invent evidence.
- **Attachment.** A design declares `rests_on:` — the corpus paths it derives from — and the
  gate fails when one is gone.
- **The effect vocabulary.** A design declares `derives_effects_from:` as `class:relationship`
  pairs, each of which must be a relationship that class declares. A design does not invent an
  effect; where the ontology has none, that absence is the finding.

Do not put a proposal in `.yidam/corpus/`, and do not put a documentary claim in `design/`.
The rule is `directories.md`'s: a new top-level directory is fine, and widening the corpus to
hold something that is not a documentary claim is not.

A **specimen** — a worked example authored in a proposed language — is a design artifact too,
and lives in `design/specimen/` as part of the proposal it exercises. It is not corpus input and
no calculator over the corpus should read it. See
[`.yidam/decisions/specimen-placement.yml`](.yidam/decisions/specimen-placement.yml).

[`design/README.md`](design/README.md) has the front-matter shape and, more usefully, what the
gate cannot catch.

## `engine/` — where this repository builds rather than proposes

The corpus records, `design/` proposes, and [`engine/`](engine/) holds the artifact both are
about. This section exists because the conflation it guards against is this repository's
characteristic hazard, named under *Conduct norms* above: `crates/` is the instrument, and a
renderer does not belong in it.

**The one rule it relaxes: it holds material that makes no claims.** Every other directory here is
prose that asserts something and carries `[verified]`, `[inference]` or `[open]`. Code carries no
tag, which is not a softening of the discipline but an exit from it — and it is a sharper
relaxation than `design/`'s, because a proposal is still held to provenance and code is outside
the scheme entirely. **The three tags cannot protect that directory.**

**The rule it does not relax: a module may not invent a subsystem.** A file that implements one
declares `realizes: subsystem/<name>` in its first ten lines — markdown front matter or a `//!`
doc comment — and the gate fails when the corpus declares no such node. The ambiguity is
deliberate and is `derives_effects_from:`'s: either the module is a component nothing has
described, or the corpus is missing one the engine has just discovered it needs. Both are
findings.

```
mise run engine-check     # cargo test -p design-gate --test engine
```

[`engine/README.md`](engine/README.md) has the contract, the four subsystems the corpus specifies,
and what the gate cannot catch.
[`.yidam/decisions/engine-directory.yml`](.yidam/decisions/engine-directory.yml) is the record,
including why `game-format` is still under `crates/` and the condition for moving it.

## Reading the corpus

**Do not navigate this corpus with `grep`.** It is a typed graph, and there are commands that
read it as one. `grep` searches text; these answer about nodes, edges and coverage.

```sh
yidam due                                    # what is owed — stale index, open questions
yidam query 'interaction -applies-> verb'    # which verbs the seeded interactions exercise
yidam query 'prior-art -exhibits-> failure-mode'  # what each engine's vocabulary permitted
yidam neighbors verb/use-with.yml            # one node's neighbourhood, both directions
yidam pack 'subsystem -realizes-> interaction' --budget 4000   # that answer as prose
```

The first of those is the central question's own arithmetic: a verb no interaction exercises
is a primitive with no demonstrated need, and an interaction reaching for a verb the
vocabulary does not declare is the vocabulary being too small. Both are findings.

**When `query` comes back empty it says why**, derived from what the corpus states rather than
guessed — *the class is not declared*, *it is declared and holds nothing*, *it holds instances
and none carries that value (and here are the values it does carry)*, *nothing authors that
relationship*. Zero `grep` hits say none of that, and a coverage gap you cannot see is one you
will fill from memory instead. Read the absence before concluding the corpus is silent.

A misspelled class or relationship is **rejected with the near miss named**, never returned as
an empty result. `mise run ci` never sees a wrong query, so this is the only thing that will
tell you.

[Reading the corpus](.yidam/.vendor/prelude/guidelines/reading-the-corpus.md) has the full
surface and the worked examples.

## The gate

`mise run ci` is what CI runs: `graph-check`, `graph-lint`, and `regen --check`. A commit
that breaks an edge, orphans a node, or leaves a REGEN block stale fails there. Run it
before committing rather than after.

**Settling a phase usually makes the gate fail until you regenerate**, and the reason is the
corpus rather than the branch. A phase that adds a node moves the node count and the claim
tallies in `README.md`'s `status` block and the table in `.yidam/corpus/README.md`, so
`mise run ci` passes on the phase branch and fails on `main` one command later, on blocks
nobody edited. The merge is not finished until:

```
git merge --no-ff -m "phase: <name> — <what it produced>" phase/<name>
git branch -d phase/<name>
mise run regen && git commit -am "regen: status block after settling phase/<name>"
```

Found by doing it — `cbd2c9b` merged green and left `main` red.

`git branch -d` itself no longer changes generated content, and it used to. The `status`
block counted phase refs, so creating or deleting a branch moved committed content with no
commit behind it: the gate could be red for the life of a phase on a file the phase never
touched, and go green when a ref was deleted rather than when anything was repaired. Watched
here across `phase/save-boundary`. `cli/v0.12.0` took the tally out of the block — a count of
refs is a property of how a checkout was fetched rather than of the commit, so no committed
value was green everywhere. `yidam phases` is where the live count belongs.

Run the composite rather than its parts. Each catches something the others do not —
`graph-check` reads the graph and is blind to a stale REGEN block; `regen --check` reads
generated content and is blind to a broken edge — and the set is held to CI's by a test
upstream, so it stays right when a gate is added.

`yidam lint` gates against `.yidam/lint-baseline.yml`, not against zero. It asks whether
*this change* made the corpus less clean, because a gate that fails on inherited debt gets
switched off and stays off. Two things fail it: an error-severity violation that is not in
the baseline, and a baseline entry that no longer occurs. The second is not a bug — a
baseline permitted to be wrong drifts, and one that over-lists silently re-permits whatever
it over-lists. Fix the corpus, then `mise run graph-lint-bless` and commit the diff.

Two checks report and never gate. `unauthored-prose-link` covers material this repository
did not author — generated output, and imports copied from elsewhere unmodified — declared in
`.yidam/authorship.yml`. Those findings are real; they are somebody else's. Fix the
generator, or raise it upstream. Do not baseline them, and do not edit an import to satisfy a
linter: that falsifies the record the import exists to keep. `authorship-region-stale` says a
declaration there no longer matches anything on disk.

`mise run graph-lint-explain` prints each check's rationale. Read it before deciding a
check is wrong.

This repository adds **one gate of its own**, and it is a test:

```
mise run design-check     # cargo test -p design-gate
```

It checks that every design document's declared premises still resolve in the corpus, that
every effect it names is a relationship the ontology declares, that a document carrying
`[verified]` cites a catalog entry, and that every `.game` specimen resolves — every operand
naming something declared, of the right kind. `mise run ci` runs it as part of `cargo test`,
and so does the `crates` CI job; there is no separate step to forget.

It was a shell script until `crates/` existed, and moved on the condition
[`.yidam/decisions/design-directory.yml`](.yidam/decisions/design-directory.yml) wrote down.
[`.yidam/decisions/domain-computer.yml`](.yidam/decisions/domain-computer.yml) records the
move and what it bought.

The other gate this repository expects to need is a vocabulary-coverage check — verbs no
interaction exercises, interactions reaching for verbs the vocabulary does not declare. It is
still unwritten, and now for a sharper reason than "not enough interactions": whether a
coverage report over a *specimen* and a calculator over *corpus instances* are one computation
with two inputs is `[open]`. Writing it before that is settled answers the wrong question
quickly.
